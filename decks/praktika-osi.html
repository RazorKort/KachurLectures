Инкапсуляция: как файл обрастает заголовками

0 / 0

Приложение отдаёт данные: файл отчёт.xlsx, 1 800 000 байт. Пока это просто поток байт без адресов.

L7 добавляет свой заголовок: метод, путь, тип содержимого — «что мы вообще просим у сервера».

L6 приводит данные к виду, понятному обеим сторонам, и при необходимости шифрует их (TLS).

L5 привязывает всё к конкретному сеансу: этот диалог отличается от десятка других на том же компьютере.

L4 режет поток на сегменты по MSS (1460 байт) и дописывает TCP-заголовок: порты, SEQ, ACK, окно.

L3 дописывает IP-заголовок: IP источника и получателя, TTL, протокол. Эти адреса не изменятся до самого конца.

L2 упаковывает пакет в Ethernet-кадр: MAC источника и получателя, тип, контрольная сумма FCS.

Правило, которое спасает на экзамене

L3 сетевой

Каждый уровень разговаривает только со своим уровнем на другой стороне. TCP отправителя — с TCP получателя, Ethernet ПК — с Ethernet коммутатора. Нижние уровни для верхних — просто транспорт.

  • IP-адреса — сквозные: от первого байта до последнего
  • MAC-адреса — локальные: меняются на каждом участке между устройствами
  • порты — принадлежат паре процессов, а не компьютерам
  • биты — существуют только внутри одного провода

Декапсуляция на приёме

L2 канальный

Получатель делает ровно обратное и на каждом уровне задаёт один вопрос — «моё ли это?»

  • L1 собрал биты в кадр → считаем FCS: не бит ли побился
  • L2: MAC получателя мой или широковещательный? иначе — выбросить
  • L3: IP получателя мой? иначе — выбросить (хост) или маршрутизировать (роутер)
  • L4: по номеру порта найти процесс, собрать сегменты в поток по SEQ
  • L7: отдать приложению готовый файл

Шаг 2 — транспортный уровень: порты и сегментация

L4 транспортный

Браузер открывает сокет: свой случайный порт 49312, порт получателя 80. Пара «IP:порт ↔ IP:порт» и есть соединение — по ней сервер отличает эту передачу от сотни других.

Поток в 1 800 000 байт не влезет в один кадр: максимум полезных данных в сегменте — MSS = 1460 байт (1500 байт MTU − 20 IP − 20 TCP). Значит получится 1234 сегмента: 1233 полных по 1460 байт и один на 820 байт.

Каждый сегмент нумеруется: SEQ — номер первого байта в потоке. Получатель подтверждает приём полем ACK. Потерянный сегмент будет повторён.

Шаг 4

ARP: IP знаем — MAC не знаем

Отправить кадр в провод можно только по MAC-адресу. У ПК-1 есть IP сервера, но карта не умеет адресовать по IP. Нужен перевод IP → MAC.

ARP-запрос и ARP-ответ

0 / 0

ПК-1 кладёт в кадр ARP-запрос: «у кого 192.168.10.10 — ответьте на A4:5E:60:1A:0C:25». MAC получателя в кадре — FF:FF:FF:FF:FF:FF, то есть «всем».

Кадр доходит до коммутатора.

Широковещательный кадр коммутатор копирует во все порты, кроме того, откуда пришёл.

Все, у кого IP не совпал, молча выбрасывают запрос — но заодно запоминают MAC отправителя.

Сервер узнал свой IP и отвечает ARP-ответом — уже лично, одному адресату.

Ответ возвращается на ПК-1 по известному коммутатору порту.

ARP-таблица заполнена. Следующие кадры пойдут сразу, без запросов — запись живёт обычно 2–4 минуты.

Шаг 6

Физический уровень: те самые нули и единицы

Кадр превращается в последовательность импульсов. Никаких адресов здесь уже нет — только уровни напряжения и время.

Байт 0xB2 в проводе

0 / 0

Берём один байт кадра — например 0xB2 = 10110010.

Простейшее кодирование NRZ: единица — есть напряжение, ноль — нет. Проблема: на длинной цепочке нулей приёмник теряет синхронизацию.

Манчестерское кодирование: в середине каждого бита обязателен переход. Синхронизация восстанавливается из самого сигнала, но нужна вдвое большая полоса.

Поэтому в гигабитных сетях применяют более экономные схемы (4B/5B, PAM-5), но принцип тот же: бит — это событие в среде, привязанное ко времени.

Что происходит в проводе

L1 физический
  • сигнал идёт по двум парам как разность напряжений — помеха одинаково влияет на обе и вычитается
  • скорость распространения ≈ 2/3 скорости света: 100 м кабеля = 0,5 мкс
  • затухание растёт с частотой — отсюда ограничение 100 м для витой пары

Чего на L1 нет

  • нет понятия «адрес»
  • нет понятия «кадр» — только биты
  • нет понимания, кому это нужно

Все решения принимаются выше. Задача L1 — донести биты без искажений.

Как проверяется целостность

Приёмник считает CRC32 по принятым байтам и сравнивает с полем FCS. Не совпало — кадр выбрасывается без уведомления. Потерю заметит TCP: не придёт подтверждение, сегмент будет отправлен повторно.

Коммутатор: три правила и одна таблица

Коммутатор работает на L2 и не знает ни одного IP-адреса. Всё его поведение описывается тремя правилами.

Обучение таблицы и передача кадра

0 / 0

ПК-1 отправляет кадр с MAC-адресом сервера в поле получателя.

Кадр приходит на порт Gi1/0/5.

Правило 1 — обучение: коммутатор смотрит на MAC источника и запоминает: A4:5E:60:1A:0C:25 находится за портом Gi1/0/5.

Правило 2 — передача: MAC получателя в таблице не найден, поэтому кадр уходит во все порты, кроме входного.

Сервер отвечает — и теперь коммутатор узнаёт, за каким портом находится его MAC.

Правило 3 — фильтрация: дальше кадры этой пары идут только между портами Gi1/0/5 и Gi1/0/1. Остальные их не видят.

1

Обучение

Запоминает MAC источника и порт, с которого кадр пришёл. Запись живёт обычно 300 секунд без трафика.

2

Передача

MAC получателя найден → отправить в один порт. Не найден или широковещательный → отправить во все, кроме входного.

3

Фильтрация

Если получатель за тем же портом, откуда пришёл кадр, — кадр не передаётся никуда.

Коммутатор принимает решение

MAC-таблица SW1 содержит только запись A4:5E:60:1A:0C:25 → Gi1/0/5. На порт Gi1/0/5 приходит кадр с получателем 00:1B:21:7F:3D:10.

MAC получателя в таблице отсутствует → кадр копируется во все порты, кроме входного (flooding). Запись об источнике уже есть, обновится только таймер. Коммутатор работает на L2 и в содержимое IP-пакета не заглядывает — IP-адреса проходят сквозь него нетронутыми.

Шаг 3

Маршрутизация: пакет едет по хопам

Каждый маршрутизатор принимает кадр, разбирает до L3, смотрит таблицу маршрутов и собирает новый кадр для следующего соседа.

Что меняется, а что остаётся на каждом хопе

0 / 0

ПК-1 отправляет кадр шлюзу: MAC свой → MAC шлюза, IP — конечные.

R1 снимает Ethernet-кадр, смотрит IP получателя и ищет в таблице маршрут.

R1 уменьшает TTL на единицу, пересчитывает контрольную сумму заголовка и собирает новый кадр — уже с другими MAC-адресами.

Заодно работает NAT: частный адрес 192.168.10.25 заменяется на внешний 95.84.17.33, а порт источника запоминается в таблице трансляций.

Дальше по интернету пакет проходит ещё десяток маршрутизаторов — и на каждом MAC-адреса переписываются заново.

Когда TTL дойдёт до нуля, пакет будет уничтожен, а отправителю придёт ICMP-сообщение — именно на этом работает tracert.

Не меняется вдоль всего пути

L3 сетевой
  • IP источника и получателя (до NAT)
  • порты TCP (до PAT)
  • сами данные приложения

Меняется на каждом хопе

L2 канальный
  • MAC источника и получателя — полностью
  • TTL — уменьшается на 1
  • контрольная сумма IP-заголовка — пересчитывается
  • FCS кадра — считается заново

Меняет NAT на границе

  • IP источника: 192.168.10.25 → 95.84.17.33
  • при необходимости порт источника
  • запись в таблице трансляций живёт, пока идёт сеанс
!

Поэтому из интернета нельзя «постучаться» на 192.168.10.25 — такого адреса в интернете не существует, он частный и повторяется в миллионах сетей. Ответ находит дорогу назад только потому, что R1 хранит строку таблицы NAT.

Шаг 4

Сообщение уходит и приходит второму пользователю

Транспортный уровень подтверждает доставку — в интерфейсе это одна галочка.

Сервер расшифровывает, сохраняет сообщение и присваивает ему номер.

У телефона Бориса давно установлено своё соединение с тем же сервером — сервер отправляет сообщение в него (push).

Клиент Бориса подтверждает получение, сервер сообщает об этом Ане — вторая галочка.

Почему нельзя отправить файл одним куском

L4 транспортный

Канальный уровень ограничивает размер кадра: MTU Ethernet — 1500 байт полезной нагрузки. Всё, что больше, либо режется на транспортном уровне (TCP), либо фрагментируется на сетевом (IP) — второй вариант хуже: потеря одного фрагмента губит весь пакет.

Поэтому TCP заранее договаривается о MSS в рукопожатии и режет поток так, чтобы IP-фрагментация не потребовалась.

Окно: сколько слать, не дожидаясь ответа

Если ждать подтверждения на каждый сегмент, на канале с задержкой 20 мс мы получим смешные 73 КБ/с. Поэтому отправитель держит в полёте целое окно.

окно 64 КБ, задержка 20 мс
64 000 Б / 0,02 с ≈ 3,2 МБ/с

окно 1 сегмент (1460 Б)
1460 Б / 0,02 с ≈ 73 КБ/с

Окно, потеря сегмента и повторная передача

0 / 0

Отправитель шлёт сразу три сегмента, не дожидаясь подтверждения — это окно.

Пришло подтверждение ACK=2921: «получил всё до байта 2920, жду 2921».

Третий сегмент потерялся — например, кадр не прошёл проверку FCS и был выброшен.

Получатель продолжает подтверждать тот же номер: дублирующие ACK — сигнал о потере.

Отправитель повторяет только потерянный сегмент, а не весь файл.

Подтверждение сдвинулось дальше — окно поехало, передача продолжается. При этом TCP на время уменьшает скорость, считая потерю признаком перегрузки.
